# Ранжирование русскоязычных поисковых результатов

## Задача и итоговое решение

В [соревновании AMML Ranking 2026](https://www.kaggle.com/competitions/amml-ranking-competition-2026) я решал задачу ранжирования: для каждого запроса нужно расположить релевантные фрагменты выше нерелевантных. Набор кандидатов уже задан, поэтому отдельный поиск документов я не реализовывал. Для каждой пары «запрос — фрагмент» моя модель вычисляет числовую оценку релевантности.

В итоговое решение я включил предобученный **Qwen3-Reranker-4B** и дообучил его LoRA-адаптеры на данных соревнования. После одной эпохи из **533 обновлений** я получил **NDCG@10 = 0,951076 на валидации** и **0,951640 на публичной части Kaggle**. При обучении использовал до 512 токенов, при получении предсказаний — до 768. Результат закрытой части соревнования на момент подготовки работы неизвестен.

Ниже я описываю, как проверял данные, сравнивал методы и пришёл к этому варианту. В `solution.ipynb` оставил только окончательную подготовку данных, обучение и получение `submission.csv`. Версии вычислительных библиотек указал в `requirements.txt`.

## 1. Проверка данных

Сначала я проверил размеры выборок, идентификаторы, пропуски, повторяющиеся фрагменты и распределение релевантности.

| Показатель | Обучающие данные | Тестовые данные |
|---|---:|---:|
| Пары «запрос — фрагмент» | 31 530 | 13 507 |
| Запросы | 3 042 | 1 305 |
| Медианное число кандидатов на запрос | 10 | 10 |
| Релевантные пары | 8 168 | Метки недоступны |

У каждого обучающего запроса были и релевантные, и нерелевантные кандидаты. Поля запроса и фрагмента были заполнены, но заголовки встречались с пропусками: 1 382 строки в обучающей выборке и 691 в тестовой. Я сохранил такие строки. Если заголовок отсутствует или после удаления внешних пробелов равен `NULL`, использую только фрагмент; иначе объединяю заголовок и фрагмент через две новые строки.

Числовые метаданные оказались неоднородными: встречались пропуски, отрицательное число фрагментов, разные разделители разрядов и противоречия между индексом фрагмента и размером статьи. Для 195 статей в объединённых данных обнаружились значения длины статьи, различающиеся ровно в тысячу раз. Поэтому я не стал автоматически считать все эти значения надёжными признаками. Их полезность проверил отдельным экспериментом.

В текстах я также обнаружил HTML-разметку, невидимые символы и следы повреждённой кодировки. Проверка сжатия пробелов устранила только 11 из 647 случаев обрезки на валидации при лимите 512 токенов. В окончательной обработке я ограничился удалением внешних пробелов и не применял глобальную очистку, которая могла бы изменить содержательные символы.

Отдельно я изучил длины входов модели. При лимите 512 токенов обрезались 3 334 из 22 116 обучающих пар и 647 из 4 702 валидационных. В одном из разобранных примеров фраза с ответом находилась за границей этого окна. Это стало основанием проверить увеличение контекста.

## 2. Валидация и метрика

Я оценивал модели по **NDCG@10**, как в соревновании. Для каждого запроса сортировал кандидатов по убыванию предсказания, при равенстве — по строковому `id` в возрастающем порядке. Идеальную выдачу рассчитывал по всем исходным кандидатам запроса, а итоговую метрику усреднял по запросам с равным весом. Запрос с нулевой идеальной оценкой должен вносить нулевой вклад.

Случайное разбиение отдельных строк здесь не подходит: кандидаты одного запроса должны оставаться вместе. Кроме того, одинаковые фрагменты встречались у разных запросов. При пробном разбиении только по запросам часть валидационных фрагментов уже присутствовала в обучающей части, тогда как между официальными train и test таких совпадений я не нашёл.

Поэтому я объединил запросы, связанные общими фрагментами, в группы и целиком распределил эти группы между тремя частями. Связи учитывал и через промежуточные запросы. По статьям дополнительную группировку не вводил: в официальных train и test встречались 777 общих статей.

| Часть | Для чего использовал | Запросы | Пары |
|---|---|---:|---:|
| Обучающая, fit | Дообучение моделей | 2 130 | 22 116 |
| Валидационная, dev | Сравнение вариантов | 456 | 4 702 |
| Контрольная | Дополнительная проверка ансамбля | 456 | 4 712 |

Во всех сравнениях я сохранял полный набор кандидатов каждого запроса. Модели обучал только на fit. В итоговом ноутбуке оставил эту же обучающую часть, чтобы воспроизводить выбранное решение.

У разбиения есть ограничение: крупнейшая связанная группа из 437 запросов целиком попала в fit. В dev и контроле нет групп размером от 17 запросов, хотя в test к ним относятся 15,5% запросов. Кроме того, dev многократно использовался для сравнения методов, а контроль я открывал при выборе ансамбля. Поэтому локальные оценки не считал гарантией такого же результата на закрытой части соревнования.

## 3. Ход экспериментов

### Первое решение: BGE и сравнение функций потерь

Я начал с мультиязычной модели **BGE-reranker-v2-m3**, которая совместно обрабатывает запрос и документ. Чтобы адаптировать её к данным соревнования, обучил LoRA-адаптеры и классификационную голову с бинарной кросс-энтропией, BCE. Это дало рост NDCG@10 на dev с **0,927617 до 0,939715**. Первая отправка получила **0,928200** на публичной части.

Затем я проверил, поможет ли другая функция потерь. Сравнил BCE с равным весом запросов и попарную RankNet, которая учит ставить релевантный фрагмент выше нерелевантного. Получил **0,939492** и **0,939209** соответственно. Убедительного преимущества перед первым вариантом не увидел и не стал продолжать подбор функций потерь для BGE.

### Переход к Qwen

Следующей гипотезой была более сильная языковая модель ранжирования. Я взял **Qwen3-Reranker-4B**, загрузил замороженную базу в 4-битном представлении и обучал только LoRA-адаптеры. Так удалось использовать модель на доступной видеокарте.

Первый запуск из-за ограничения времени закончился после 349 из 533 запланированных обновлений. На dev я получил **0,944466**, на публичной части — **0,943139**. При повторном обучении этого варианта получил **0,945682** и **0,943629**. Qwen стал основной моделью для дальнейшей работы. Последующие изменения шага и длины входа я сравнивал на одной сохранённой траектории обучения.

### Проверка ансамбля Qwen и BGE

Поскольку ошибки двух моделей частично различались, я проверил объединение их предсказаний. Сравнивал нормировку оценок внутри запроса и объединение по рангам. Лучший предварительный результат дало среднее с весами 50/50 после min–max-нормировки.

При повторном обучении ансамбль получил **0,956334 на dev**, тогда как отдельный Qwen — **0,945682**. На контрольной выборке преимущество оказалось заметно меньше: **0,945900 против 0,944456**. Интервал разницы включал ноль. По принятому на этом этапе правилу положительной средней разницы я всё же выбрал ансамбль, но его публичный результат составил **0,939590**, ниже **0,943629** у одиночного Qwen.

После этой проверки я вернулся к Qwen. Таким образом, публичная оценка тоже участвовала в выборе, и я не рассматриваю её как полностью независимую проверку всех исследовательских решений.

### Проверка лексических признаков и метаданных

Затем я проверил, можно ли дополнить Qwen информацией, которую текстовая модель использует неявно или не использует вовсе. Обучил отдельные модели на лексических признаках, а затем добавил метаданные и признаки качества данных.

Добавление этих признаков улучшило результат градиентного бустинга с **0,708328 до 0,763764** на dev. Но смесь его оценок с Qwen в пропорции 10/90 получила **0,948678**, а интервал прибавки к Qwen включал ноль. Я сделал вывод, что в метаданных есть сигнал, но устойчивую пользу их добавления к основной модели пока не подтвердил. В финале оставил запрос, заголовок и фрагмент.

### Завершение эпохи и увеличение контекста

К этому моменту Qwen ещё не прошёл все обучающие примеры. Я продолжил обучение с 349 до 533 обновлений, сохранив прежние настройки и расписание скорости обучения. На обоих состояниях проверил длины инференса 512 и 768 токенов; длина обучения оставалась 512.

До сравнения я задал правило: новый вариант должен улучшить NDCG@10 не менее чем на 0,002 относительно исходного 349/512, а нижняя граница парного 95%-го интервала должна быть положительной. Интервалы оценивал на 20 000 повторных выборках целых групп связанных запросов. Среди прошедших правило вариантов выбирал максимальный dev.

Лучшим оказался вариант **533 обновления и 768 токенов на инференсе**: **0,951076 на dev** и **0,951640 на публичной части**. Относительно 349/512 его прирост на dev составил 0,005395; улучшились 41 запрос, ухудшились 17. Основное улучшение связано с завершением обучения. Отдельная прибавка от длины 768 вместо 512 после 533 обновлений была меньше, 0,000908, и её интервал включал ноль.

### Последние проверки

После выбора основной конфигурации я проверил ещё четыре гипотезы:

- **Контекст 1024 токена.** Dev вырос только до 0,951115. Прибавка была слишком мала для принятого правила.
- **Дополнительное обучение.** Ещё 267 обновлений с меньшей скоростью обучения, до 800 суммарно, дали 0,950636. Этот вариант оказался хуже выбранного.
- **Более подробная инструкция модели.** При тех же весах и доступных токенах документа dev снизился до 0,943571. Я сохранил исходную инструкцию.
- **Полный контекст длинных фрагментов.** Для 136 валидационных пар, не помещавшихся в 768 токенов, я обработал полный текст. Dev составил 0,951964, но прибавка 0,000887 не достигла порога 0,002, а интервал включал ноль.

Эти проверки не дали достаточных оснований менять финальную конфигурацию. Повторные отправки после них содержали те же предсказания выбранной модели.

## 5. Что вошло в окончательное решение

В `solution.ipynb` я использую [закреплённую публичную ревизию Qwen3-Reranker-4B](https://huggingface.co/Qwen/Qwen3-Reranker-4B/tree/22e683669bc0f0bd69640a1354a6d0aebcfeede5). Модель получает инструкцию, запрос и документ одним входом. Оценку релевантности рассчитываю как разность логитов ответов `yes` и `no` на последней позиции.

| Настройка | Выбранное значение |
|---|---|
| Обучаемая часть | LoRA в `q_proj` и `v_proj`; 2 949 120 параметров |
| Настройки LoRA | Ранг 8, alpha 16, dropout 0,05 |
| База модели | Заморожена; NF4 с двойным квантованием, вычисления FP16 |
| Обучающие данные | 22 116 пар из 2 130 запросов, одна эпоха |
| Обновления | 533; до четырёх целых запросов за обновление, микробатч из двух пар |
| Функция потерь | BCE по парам с накоплением градиентов внутри обновления |
| Оптимизатор | AdamW, начальная скорость 0,00005, weight decay 0,01 |
| Изменение скорости обучения | Разогрев 22 обновления, далее косинусное снижение до 35% исходной скорости |
| Длины входа | 512 при обучении, 768 при инференсе |
| Воспроизводимость | Фиксированное разбиение и порядок обучения, seed 2026 |

Для собственного дообучения я использовал только данные соревнования. Внешние обучающие наборы и псевдоразметку test не добавлял. Финальный ноутбук заново обучает адаптер из публичных исходных весов и не требует файлов моих промежуточных экспериментов.

## 6. Как повторить решение

Исследовательские запуски я выполнял на **Linux, Python 3.13.16 и NVIDIA Tesla T4**. Итоговый ноутбук подготовил для обычного Jupyter вне Kaggle. Для него нужны Linux x86_64, совместимая NVIDIA GPU с видеопамятью от 14 ГиБ и драйвер для закреплённой CUDA-сборки PyTorch. Обучение на Mac через CPU или MPS в этой реализации не предусмотрено.

Для повторения предусмотрел следующий порядок:

1. Скачать три файла репозитория и официальные CSV соревнования. Положить `train.csv`, `test.csv` и `sample_submission.csv` в папку `data` рядом с `solution.ipynb`.
2. В Python-окружении, которое используется выбранным ядром Jupyter, установить зависимости:

   ```bash
   python -m pip install -r requirements.txt
   ```

3. Перезапустить ядро, открыть `solution.ipynb`, проверить пути в первом блоке и выполнить **Run All**. При первом запуске нужен интернет для скачивания публичных весов и не менее 12 ГиБ свободного места для их кеша.
4. Забрать готовый файл `outputs/qwen-final-01/submission.csv`. В нём будут столбцы `id,prediction` и предсказания для всех 13 507 тестовых строк. Для нового запуска нужно изменить `run_id`, чтобы сохранить результаты предыдущего.

Предполагается, что Jupyter уже установлен. При необходимости саму среду ноутбуков можно установить командой `python -m pip install jupyterlab ipykernel`.

Полный путь на T4 я оцениваю в **5,5–6,5 часа** по времени исследовательских этапов. Во время исследования обучение и получение предсказаний были выполнены последовательно в нескольких сеансах. **Полный запуск этой окончательно оформленной версии от начала до конца вне Kaggle я пока не проводил.**
