# AMML Ranking 2026 · ранжирование фрагментов с Qwen

**Итоговый результат** — NDCG@10 **0.9510764655571348 на dev** и **0.951640 на public**. Результат private неизвестен. Для каждой заданной пары «русскоязычный запрос — фрагмент» решение вычисляет один score. Выбран один Qwen3-Reranker-4B с обученным LoRA-адаптером после 533 обновлений. При обучении использовалось окно 512 токенов, при инференсе — 768. [Соревнование на Kaggle](https://www.kaggle.com/competitions/amml-ranking-competition-2026)

## Данные и метрика

| Показатель | Train | Test |
|---|---:|---:|
| Пары «запрос — кандидат» | 31 530 | 13 507 |
| Запросы | 3 042 | 1 305 |
| Уникальные фрагменты по `document_id` | 27 703 | 11 885 |
| Кандидатов на запрос, минимум / медиана / максимум | 2 / 10 / 19 | 2 / 10 / 17 |
| Пары с меткой 1 | 8 168 (25,9%) | |

В train у каждого запроса есть и релевантные, и нерелевантные фрагменты. Для оценки кандидаты каждого запроса сортируются по убыванию score, при равенстве — по строковому `id` в возрастающем порядке. Для бинарной метки вклад кандидата на позиции $r\leq 10$ равен $\mathrm{relevance}_r/\log_2(r+1)$. Сумма вкладов делится на идеальную сумму, рассчитанную по **всем** исходным кандидатам запроса. При нулевом идеальном значении запрос получает 0. Итог — среднее по запросам с равным весом. В public входят 392 тестовых запроса, в private — 913.

### Какие свойства данных повлияли на решение

- Поля `query` и `text` заполнены во всех строках. Пустой или пробельный `title` встречается в 1 382 обучающих и 691 тестовой паре. Такие пары сохранены. Если заголовок после удаления внешних пробелов пуст или равен точной строке `NULL`, модель получает только фрагмент. В остальных случаях документ имеет вид `title + "\n\n" + text`.
- Метаданные неоднородны. В train у 1 398 строк отсутствует `passage_index`, у 1 959 — `article_passage_count`. Число фрагментов иногда равно −1. На 194 строках с обоими значениями в виде целых без знака индекс превышает заявленное число фрагментов. В `article_char_count` встречаются разные разделители разрядов, а у 195 статей в объединённых train и test встречаются значения, различающиеся ровно в тысячу раз. Метаданные и источник загрузки участвовали в отдельных диагностических моделях. Финальный Qwen использует текст запроса, заголовок и фрагмент.
- В текстах видны следы загрузки. На dev в 60 строках обнаружены HTML-теги, в 44 — HTML-сущности, в 58 — невидимые символы или мягкий перенос, в 13 — признаки повреждённой кодировки, в 58 — навигационные вставки. Глобальная чистка могла изменить содержательные символы. Сжатие пробелов устранило лишь 11 из 647 обрезок на dev при лимите 512. В итоговом решении сохранён исходный текст с удалением внешних пробелов.
- Медиана / 95-й процентиль длины `text` в train — 662 / 1 528 символов. У полного входа Qwen на fit эти величины составили 346 / 670 **токенов**. При лимите 512 обрезались 3 334 из 22 116 fit-пар. Удлинение инференса до 768 сократило количество обрезанных пар с 647 до 136 на dev и с 1 994 до 415 на test. Обрезается хвост документа, сохраняются запрос и служебный суффикс. В одном dev-примере фраза с ответом о жене Берроуза оказалась за границей 512 и поместилась в 768. Были и ошибки на коротких текстах, например при различении Наташи Ростовой и других членов семьи.

## Валидация

Разбиение v1 сохраняет все пары одного запроса вместе. Повторов запроса под разными ID при сравнении исходного и нормализованного текста не обнаружено. Один и тот же **фрагмент** мог встречаться у разных запросов. При пробном разбиении только по запросам 741 пара dev содержала точный фрагмент из fit, тогда как между официальными train и test таких совпадений нет. Поэтому запросы, связанные хотя бы одним общим фрагментом, объединены в компоненты, включая транзитивные связи. Между частями v1 пересечений по запросам и фрагментам нет. Статьи могут пересекаться между частями. Такое разбиение соответствует официальным train и test, где встречаются 777 общих статей. Объединение по статьям связало бы в одну компоненту 1 654 запроса.

| Часть v1 | Запросы | Пары | Позитивы |
|---|---:|---:|---:|
| Fit | 2 130 | 22 116 | 5 707 |
| Dev | 456 | 4 702 | 1 206 |
| Контроль | 456 | 4 712 | 1 255 |

Модель обучалась только на fit. На dev оценивались все кандидаты каждого исходного запроса. Крупнейшая связная компонента из 437 запросов целиком вошла в fit. В dev и контроле нет компонент от 17 запросов, хотя к ним относятся 15,5% запросов test. Направление возможного смещения NDCG неизвестно. Dev многократно использовался при выборе вариантов, контроль открывался в D04. Парные интервалы ниже получены пересэмплированием целых компонент с пересчётом среднего по запросам.

## Как обучается финальная модель

База и токенизатор берутся из публичной ревизии `22e683669bc0f0bd69640a1354a6d0aebcfeede5`. Модель читает инструкцию, запрос и документ одним входом. Исходная инструкция Qwen — `Given a web search query, retrieve relevant passages that answer the query`. Score равен разности логитов токенов `yes` и `no` на последней позиции. [Закреплённая ревизия Qwen3-Reranker-4B](https://huggingface.co/Qwen/Qwen3-Reranker-4B/tree/22e683669bc0f0bd69640a1354a6d0aebcfeede5)

| Параметр | Значение |
|---|---|
| Обучаемая часть | LoRA на `q_proj` и `v_proj` в 36 слоях, 2 949 120 параметров в 144 тензорах FP32. Ранг 8, alpha 16, dropout 0.05 |
| Замороженная база | 4-битное NF4 с двойным квантованием, вычисления в FP16, gradient checkpointing |
| Порядок fit | seed 2026, одна эпоха. Четыре целых запроса за обновление, два в последнем. Внутри обновления пары упорядочены по длине и строковому ID. Первым выполняется самое затратное по токенам обновление |
| Функция потерь | BCEWithLogits на разности логитов. Сумма потерь по микробатчу (до двух пар) делится на число пар во всём обновлении. Градиенты накапливаются до обработки всех его пар |
| Оптимизатор | AdamW, LR 0.00005, weight decay 0.01, `fused=False`, ограничение нормы градиента 1 |
| График LR | 533 обновления, первые 22 — разогрев, далее косинусное снижение до 0.35 от исходного LR |
| Инференс | Все 13 507 кандидатов, лимит 768 токенов, batch size 8 |

Автономный запуск строит split из исходного train, инициализирует новый адаптер на публичной базе и исполняет весь план с первого шага. Вокруг технических проверок сохраняется и восстанавливается состояние генераторов случайных чисел. Перед итоговым инференсом восстанавливается собственный checkpoint шага 533. Внешние обучающие примеры и псевдометки test в обучении не использовались.

## Запуск в локальном Jupyter

Для вычислений требуется Linux x86_64 с драйвером NVIDIA, совместимым с PyTorch `2.11.0+cu130`. Ноутбук использует одну карту `cuda:0` и проверяет compute capability от 7.5 и как минимум 14 ГиБ видеопамяти. Фактическая модель GPU, память, версия CUDA и версии пакетов записываются в `run_summary.json`. Исследовательские этапы прошли на Tesla T4. Выполнение на других моделях GPU пока не проверялось.

1. Скачайте репозиторий или распакуйте архив сдачи. Перейдите в каталог с `solution.ipynb` и `requirements.txt`. Команды ниже выполняются из этого каталога.
2. Установите зависимости в Python-окружение выбранного ядра Jupyter командой `python -m pip install -r requirements.txt`, затем перезапустите ядро. Для создания отдельного окружения с JupyterLab используйте Python 3.13.16.

   ```bash
   python3.13 -m venv .venv
   source .venv/bin/activate
   python -m pip install -r requirements.txt jupyterlab ipykernel
   python -m ipykernel install --sys-prefix --name amml-ranking --display-name "Python (AMML Ranking)"
   ```

   В `requirements.txt` указан официальный индекс CUDA-сборки PyTorch. Ноутбук проверяет установленные версии. При конфликте с необязательным `torchao==0.10.0` выберите чистое окружение с этими зависимостями.
3. Самостоятельно получите три исходных CSV соревнования и разместите их рядом с ноутбуком в `data/train.csv`, `data/test.csv` и `data/sample_submission.csv`. Первый запуск скачает публичную ревизию Qwen в `.cache/amml-qwen4b/`. Для кеша требуется от 12 ГиБ свободного места. Ноутбук сам построит split из train.
4. Откройте `solution.ipynb` в Jupyter. Для созданного выше окружения выполните `python -m jupyterlab solution.ipynb` и выберите ядро **Python (AMML Ranking)**. Проверьте первый блок `CONFIG` и нажмите **Run All**. Относительные пути отсчитываются от рабочей папки ноутбука. По умолчанию `max_run_minutes=None` отключает лимит. Чтобы ограничить сеанс, укажите положительное число минут, например `480`.
5. Готовый файл появится в `outputs/qwen-final-01/submission.csv`. Перед записью проверяются завершение шага 533, конечность прогнозов и порядок всех 13 507 ID по образцу. Полные checkpoints находятся в подкаталоге `artifacts/` того же запуска. При остановке до завершения итоговый CSV не выдаётся. Для следующего запуска задайте в `CONFIG` новое имя `run_id`.

**Время на T4.** Ориентир полного пути от публичных весов до CSV — **5,5–6,5 часа** с подготовкой. Это оценка по измеренным этапам. Исследовательский сеанс D06 занял 3 ч 40 мин, начался с шага 349 и включал четыре оценки dev. Из этого времени около 52 мин занял полный инференс test при 768.

## Что подтверждено

Историческая среда Kaggle — Linux x86_64 с ядром 6.18.55+, glibc 2.39, Python 3.13.16, Tesla T4 и CUDA 13.0. Public 0.951640 подтверждён скриншотом результата D06. С предыдущим принятым ноутбуком дословно совпадают 62 определения, включая модель, токенизацию, план обучения, обработку RNG, оптимизатор, checkpoint и скоринг. При проверке предыдущей упаковки маленькая модель Qwen с LoRA прошла на CPU четыре обновления и выдала тестовый CSV. В текущей сборке локальное ядро Jupyter на macOS прочитало исходные CSV, построило split и остановилось на проверке Linux до обращения к GPU. Полный чистый Run All итогового ноутбука на Linux/NVIDIA CUDA и чистая установка в таком окружении не выполнялись. Хеши checkpoint и submission в таблице относятся к принятому запуску D06.
